# Kase 1.3.3

**Released:** 2026-11-08 · **Type:** patch release · **Breaking changes:** none

After the AirPods come back from your iPhone, Kase now catches an AirPods output that PipeWire could not start, and rebuilds it instead of reporting it fixed.

## Fixed

- **No sound on the PC after the AirPods come back from the iPhone.** When Kase takes the AirPods back, it rebuilds the PC's audio output. Sometimes the AirPods are still finishing with the iPhone and refuse to start the stream. The AirPods output on the PC then sits in PipeWire's error state: it plays nothing, apps such as EasyEffects move to another output (the monitor's speakers), and Discord's voice stream times out. Kase 1.3.2 checked only whether anything was playing on that output, found nothing, and logged "recovered at step 1". Now an output in the error state counts as broken. A rebuild does not count as done while the output is still in that state, so Kase moves on to the next recovery step. While Kase is watching the AirPods, it also rebuilds an output it finds in that state, even with nothing playing on it. The log says `the AirPods output is in an error state`.

## How it was checked

- **On David's PC (8 November, 1.3.1):** after a YouTube video on the iPhone, Kase took the AirPods back at 12:25:34Z. bluetoothd logged `START request rejected: Bad State`, WirePlumber logged `Acquire ... returned error`, and the AirPods output went into the error state, while Kase logged `recovered at step 1`. Game and Plex audio went to the HDMI monitor, and Discord's voice streams timed out before Discord restarted. Turning the AirPods profile off and back on by hand brought the output back.
- **Tests:** two new audio guard tests. One rebuilds an output in the error state with nothing playing on it. The other checks that a toggle leaving the output in that state is not reported as recovered. All 434 library tests and 94 island tests pass, and clippy and rustfmt are clean.
